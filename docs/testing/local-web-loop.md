# Local synthetic web purchase loop

Builder lane: `claude/local-web-loop`. Base commit 9584ace. Synthetic data only; no supplier, no real
order, no publication, no paid service, no credential change, no commit or push from this lane.

This document is the setup and limits reference for `apps/web`, plus the retained RED/GREEN evidence
for the work. It records what was actually run here and what remains for the coordinator.

## What exists

A Next.js App Router application at `apps/web` that drives the existing local API through a
server-side backend-for-frontend (BFF):

1. Sign in against the existing local synthetic OIDC provider with authorization code + PKCE.
2. Choose one of the seeded synthetic organisation/branch scopes; the choice is confirmed against
   `GET /v1/context` before it is stored.
3. Load a need by UUID and read back its pack reference, exact outstanding quantity and version.
4. Request a quote, then read the returned lines, total, currency, expiry, binding status, pricing
   rule and terms hash.
5. Approve with an explicit click. The idempotency key is minted and held on the server, so a retry
   after a transport failure reuses it and a re-quote cannot.
6. Load the resulting order intent and read its state, external identities and uncertainty.
7. Confirm a receipt for the remaining shipped quantity of each line with a stable server-held
   receipt reference.

The app has its own `package.json`, lockfile, `tsconfig.json`, ESLint config and test runner. It adds
no dependency to the repository root and imports no backend module.

from a validated origin plus a fixed path template plus a canonical UUID.

## Security decisions and their limits

- **Tokens are server-only.** The access token is held in the server-side session map. It is never
  written to a cookie, a response body, a header or the rendered page. A regression test asserts the
  token string appears in no login or purchase-loop response. There is no `localStorage` or
  `sessionStorage` use at all, and a test asserts both are empty after a full flow.
- **The session cookie is opaque, `HttpOnly`, `Path=/`, `SameSite=Lax`, with a bounded `Max-Age`.**
  `Secure` is deliberately omitted because the app is only ever served over plain http on the
  loopback interface. This is a development-only choice and must not be carried to any deployment.
- **In-memory session storage is development-only and refused in production.** Sessions live in the
  dev-server process and are lost on restart. `createInMemorySessionStore` throws when `NODE_ENV` is
  `production`. Construction is lazy so that `next build` (which sets `NODE_ENV=production`) still
  works; `next start` is therefore intentionally not usable, and no `start` script is provided.
- **Session lifetime never outlives the access token.** It is `min(now + sessionMaxSeconds,
  accessTokenExpiry)`. The local provider issues 300-second access tokens and no refresh grant is
  requested, so signing in again is the only way to continue. Expect to re-authenticate every five
  minutes; that is the intended behaviour, not a defect.
- **CSRF and foreign origins.** Every state-changing BFF call requires an `Origin` header exactly
  equal to the configured web origin (a missing `Origin` is treated as foreign, not trusted), a
  `Sec-Fetch-Site` of `same-origin` when the browser sends one, and an `x-pharmacart-csrf` header
  matching this session's CSRF token under a constant-time comparison. The origin check runs before
  the session lookup, so a cross-site POST learns nothing about session existence.
- **Login state and the PKCE verifier stay on the server** behind a single-use opaque handle in an
  `HttpOnly` cookie. A replayed callback, a mismatched `state` or a missing handle refuses and
  creates no session.
- **No nonce, deliberately.** A nonce binds an ID token to one login attempt. This app consumes no
  ID token: the subject it displays comes from the API's `GET /v1/context`, which the API derives
  from the `sub` of an access token it verified itself against the provider's JWKS
  (`packages/auth/src/verify-access-token.ts`). Sending a nonce nothing checks would assert a
  binding nothing enforces. The authorization code is bound by PKCE and by server-held `state`,
  which is what a code flow relies on. Two tests pin this: one asserts no `nonce` leaves the
  authorization request, the other asserts no `id_token` reaches the caller of the token exchange.
  **If an ID token is ever consumed here, a nonce must be sent and verified against it at the same
  time, along with `iss`, `aud`, `exp` and the signature.** The second test fails the moment an ID
  token starts flowing, which is the signal to do that work.
- **Bounded reads.** BFF request bodies are bounded to 8 KiB *of bytes*: a declared `Content-Length`
  over the bound is refused before the body is touched, and otherwise the stream is counted as it
  arrives and abandoned the moment the running total passes the bound. API calls omit credentials,
  refuse redirects and time out after 10 seconds.
- **Bounded growth.** Both server-side maps are swept of expired entries and capped at 256 on
  insert, oldest evicted first. `GET /auth/login` needs no session, so pending logins are the one
  allocation an unauthenticated caller controls; without a cap a stream of abandoned sign-in starts
  grows this process for as long as it runs.
- **No invented identity.** "Signed in as" shows only what the API reported. If `/v1/context` ever
  omits `userSubject`, the session subject is `null` and the page says `unknown subject`; it is
  never filled in from the subject the seed script happens to pair with the chosen scope.
- **Quantities are canonicalised, not reshaped.** `packages/contracts` refuses a trailing fraction
  zero, but `1.50` and `2.0` are what a person types and what a number input produces. The form
  rewrites them to `1.5` and `2` — the same value — so the operator never collides with a schema
  refusal naming a canonical decimal the form never mentioned. Anything that is not a plain
  non-negative decimal is reported as a mistake, not rewritten, and no request is sent.
- **No supplier dispatch control.** The app never triggers submission, reconciliation or any worker
  action. It only relays operator intent to existing API routes.
- **No bypass switches.** There is no development login shortcut, no fake session and no hardcoded
  secret. The only way to obtain a session is a real authorization-code flow against the local
  provider.

## Honest limits of this slice

- **No listing endpoints exist**, so scope, supplier and need selection use explicit synthetic
  fixture selectors mirroring `packages/db/scripts/seed-local.ts`. They are an allowlist, not
  fabricated backend data: an entry outside the list is refused before any request, and the API still
  enforces membership independently. A test reads the seed script and fails if those identifiers
  drift.
- **Quotes are box-only, cash, single-line.** The seeded catalogue carries one sale unit and the API
  exposes no unit metadata, so the request is fixed to that unit and to `paymentTerm: "cash"`, and
  the form quotes one need at a time. This is a deliberate fixture-scope restriction, stated in the
  UI as well as here.
- **Order lines only appear after backend dispatch.** `GET /v1/orders/{id}` returns lines from
  `order_line`, which the worker writes when it submits the intent. Until then the order shows state
  `queued` with no lines, and the UI says so explicitly and offers no receipt form. Exercising the
  receipt step end to end therefore requires the coordinator to run the existing worker; this lane
  did not run it.
- **The quote countdown is event-driven, not polled.** One timer fires at the expiry instant to
  disable approval. If the browser was asleep, the API's own `REQUOTE_REQUIRED` refusal is surfaced
  as a clear "request a new quote" message instead.
- **English only.** No Arabic or RTL work was done. **AC-018 is not claimed and must not be moved.**
- **No acceptance criterion is claimed by this lane.** The evidence below is unit, contract and
  render evidence with mocked HTTP dependencies. It is not an authenticated end-to-end run against
  PostgreSQL, and it does not advance AC-001 through AC-018.

### Review pass

A second pass reviewed the slice against OIDC PKCE/state/nonce, BFF cookie and token secrecy,
CSRF/origin, open redirects and SSRF, explicit approval and retry, and dependency and build pinning.

Verified and left alone:

- **PKCE and state.** S256 only, verifier and state generated per attempt and held server-side behind
  a single-use handle. The verifier never leaves the server and never appears in the authorization
  URL. Discovery endpoints are refused unless they sit on the configured issuer origin.
- **Nonce.** Correctly absent; see the security decision above for why, and for the condition that
  would make it required.
- **Token secrecy.** The access token exists only in the server-side session map. Tests assert it
  appears in no login or purchase-loop response, and that `toSessionView` exposes exactly `subject`,
  `scope`, `csrfToken`, `expiresAt`.
- **CSRF and origin.** Origin is required outright and checked before the session lookup; a
  `Sec-Fetch-Site` other than `same-origin` is refused; the CSRF token is compared in constant time.
  Cross-origin reads of `GET /api/bff/session` are blocked by the absence of any CORS header, which
  is the default and is not overridden anywhere.
- **No open redirect.** Every `Location` this app emits is either the configured web origin plus a
  fixed path and a fixed literal error code, or the authorization URL built from a discovery
  endpoint already pinned to the issuer origin. No request input reaches a `Location`.
- **No SSRF.** The only outbound callers are `api-client.ts` and `oidc.ts`. Both pin their base to a
  validated loopback origin and build every path from a fixed template plus a canonical UUID. Both
  omit credentials, refuse redirects and time out.
- **Approval and retry.** Approval happens only on a direct click, never on mount, render or reload.
  One idempotency key per quote version per session means a transport retry reuses it and a re-quote
  cannot. The key is session-scoped, so a session that expires mid-flow mints a new one — that is
  safe because the API returns the existing approval with 200 when the quote is already approved
  (`packages/db/src/procurement.ts`), rather than approving twice.
- **Pinning.** All 15 dependencies are exact versions, `engines.node` and `packageManager` are
  pinned, `npm audit` reports 0 vulnerabilities, and `next build` succeeds.

Fixed, each with its own RED/GREEN below:

1. **The 8 KiB body bound did not bound anything that mattered.** `readBody` called
   `request.text()` — buffering the whole body — and only then measured `text.length`, which counts
   UTF-16 code units. A multi-megabyte POST was read in full before its 413, and a multi-byte body
   passed at up to several times the intended size. Now the declared `Content-Length` is refused up
   front and the stream is counted in bytes and abandoned on overflow.
2. **Pending logins and sessions grew without bound.** Neither map was ever swept; entries went only
   when consumed or read after expiry. `GET /auth/login` needs no session and is reachable as a
   cross-site top-level navigation, so abandoned sign-in starts accumulated for the life of the dev
   server. Both maps are now swept and capped at 256, oldest evicted first.
3. **A missing `userSubject` was filled in from the fixture list.** `selectScope` fell back to the
   subject the seed script pairs with the chosen scope, putting a fabricated identity behind "Signed
   in as". It is now `null`, and the page already renders that as `unknown subject`.
4. **An ordinary quantity entry was refused with an opaque message.** `1.50` and `2.0` are not
   canonical decimals, so the contract schema rejected them — after a round trip, with a message
   about a canonical decimal the form never mentioned. The form now canonicalises the operator's
   entry to the identical value in the required shape, and reports a non-numeric entry itself
   without sending a request.

Nothing in this pass changed `infra/oidc/provider.ts`, which still differs from the base commit only
by the appended second client.

### What the regression tests actually pin

- Destinations: remote hosts, non-loopback hosts, paths, queries and credentialed URLs are refused
  as API, issuer and web origins.
- OIDC: S256 challenge matches the RFC 7636 reference vector; the authorization URL carries state,
  PKCE and the pinned resource and never the verifier; discovery documents that move an endpoint off
  the issuer origin are refused; token responses without a bearer token or a usable expiry are
  refused; a token-endpoint error is surfaced rather than treated as success; no `nonce` is sent and
  no `id_token` reaches the caller, so consuming one cannot pass unnoticed.
- Session: production is refused; the identifier is opaque and unrelated to the token; expiry never
  exceeds the token expiry; expired sessions are evicted and read as unauthenticated; the browser
  view has exactly `subject`, `scope`, `csrfToken`, `expiresAt`; expired pending logins and sessions
  are swept, both maps are capped, and eviction is oldest first so the newest sign-in still completes.
- Body bounds: a declared oversized `Content-Length` is refused before the body is touched; the bound
  is measured in bytes, not UTF-16 code units; an oversized stream is abandoned within a few chunks
  rather than buffered whole; a body inside the bound still succeeds.
- Reported identity: a context response without `userSubject` yields a `null` subject, and the
  fixture's seeded subject appears nowhere in the response.
- Quantities: trailing fraction zeros and leading zeros are rewritten to the identical canonical
  value; negatives, exponents and stray characters are refused; a non-numeric entry produces an alert
  and no request; a cleared receipt line is left out rather than sent as an empty quantity.
- Login: a replayed code, a mismatched state and a missing handle each refuse and create no session;
  the login cookie is single-use and cleared.
- CSRF/origin: foreign origin, absent origin, cross-site fetch metadata, absent CSRF token and
  mismatched CSRF token are each refused before the API is touched.
- Idempotency: the same quote version reuses one key across a transport failure and its retry; a
  different quote gets a different key; receipt references are stable per intent and quantity set and
  differ for a different quantity set.
- Relay honesty: 401, 403, 404 and 409 are passed through unchanged; a transport failure is reported
  as 502 `UPSTREAM_UNAVAILABLE` with an explicitly unknown outcome, never as success or as a clean
  failure.
- Interaction: no approval request is made on mount or render; approval happens once per click; an
  expired quote disables approval and demands a new one; a changed need surfaces a re-quote message
  and produces no approval; receipts are bounded to the remaining shipped quantity; nothing is stored
  in the browser; the flow is reachable by keyboard with labelled controls and a heading hierarchy.
